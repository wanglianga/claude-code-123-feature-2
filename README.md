# 基层法院诉前调解排期与协议履行平台

面向基层法院的诉前调解一体化平台：当事人在线提交申请 → 立案窗口分流 → 调解中心按案由/专长/双方时间/外地当事人智能排期 → 调解员线上线下调解并记录 → 协议人脸核验与线上签署 → **分期履行跟踪（按期提醒付款、上传凭证、确认收款/收款异议）→ 某期逾期调解员发起回访、双方提交未付款说明/收款异议、调解员决定继续履行观察（观察期随反馈重新计算）→ 法官助理同步查看并判断司法确认或后续执行线索** → 回访、司法确认或转立案。**所有角色围绕同一案件推进，全部过程统一进入案件时间线，多次改期、失联、部分履行、逾期回访、履行观察等情形可一键汇编成连续材料卷提交法官，避免在调解与立案窗口间反复补材料。**

## 技术栈

- 后端：Java 17、Spring Boot 3.2、Spring Data JPA
- 数据库：**默认 H2 内存库（MySQL 兼容模式），免安装零配置**；同时提供 MySQL 连接配置
- 前端：Vue 3 + Vite + Element Plus + ECharts
- 鉴权：登录令牌（内存 Token 存储，Bearer 头）

## 本地启动

### 方式零：Docker 一键启动（推荐，免装 JDK/Node/Maven）

前置：本机已安装 Docker（含 Compose 插件）。在项目根目录执行：

```bash
docker compose up -d --build
```

镜像采用多阶段构建（Node 构建前端 → Maven 构建后端 → JRE 运行），启动后浏览器打开 <http://localhost:8080/> 即可，前后端同源。付款凭证/异议材料附件持久化在命名卷 `mediation-attachments`。停止用 `docker compose down`。

> 说明：本仓库默认使用 H2 内存库，容器无需依赖数据库；如需 MySQL，可用 `--spring.profiles.active=mysql` 并自行提供数据库。

### 方式一：单 jar 启动（已构建好前端产物）

前置：JDK 17、Maven 3.8+。

```bash
cd backend
mvn package -DskipTests
java -jar target/mediation-platform.jar
```

浏览器打开 <http://localhost:8080/> 即可（前后端同源，无需额外启动前端）。
H2 控制台（可选）：<http://localhost:8080/h2-console>，JDBC URL `jdbc:h2:mem:mediation`，用户名 `sa`，密码空。

### 方式二：前后端分离开发（热更新）

```bash
# 终端1：后端
cd backend && mvn spring-boot:run

# 终端2：前端（5173 端口，/api 自动代理到 8080）
cd frontend && npm install --cache /tmp/npm-cache && npm run dev
```

打开 <http://localhost:5173/>。

### 使用 MySQL（可选）

1. 本机 MySQL 8，账号 root/root（或修改 `application.yml` 中 `mysql` profile 的用户名密码）；
   连接串带 `createDatabaseIfNotExist=true`，库 `court_mediation` 会自动创建，表由 JPA 自动建立。
2. 以 mysql profile 启动：

```bash
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=mysql
# 或 jar 方式：java -jar target/mediation-platform.jar --spring.profiles.active=mysql
```

## 业务功能与对应操作

1. **申请登记**：「新建调解申请」记录五类案由（民间借贷/物业费/交通事故/邻里/小额买卖）、诉求金额、被申请人联系方式、证据清单、是否愿意线上调解、紧急程度、外地当事人标识。
2. **窗口分流**：案件详情 →「分流与排期」，核验材料（缺件可先行调解并登记补正）、确定线上/线下（外地当事人自动提示线上）、从名册指派调解员。
3. **智能排期**：选择时间段后系统按「案由专长匹配 + 在办量 + 时间冲突」综合打分推荐调解员；排期自动检测调解员时段冲突；每次**改期保留原记录**、累计改期次数，≥2 次触发红黄预警。
4. **调解过程**：逐次记录争议焦点、双方让步、协商过程与结果；支持电子送达（短信/邮件/站内，无有效号码自动失败留痕）、失联登记/恢复、证据补正。
5. **协议与签署**：起草协议（一次性/分期、付款计划、担保人、履行期限、是否申请司法确认，自动生成规范文本）→ 模拟人脸核验（任意非 `0000` 的证件后四位通过，`0000` 演示不通过）→ 双方线上电子签名，签后协议生效。
6. **分期履行跟踪（按期提醒 → 凭证 → 收款确认）**：按协议生成一期或多期付款节点；平台对临期/到期未结清节点**按期提醒**付款并提示上传凭证（每日定时扫描，页面提供「立即发送按期提醒」）；付款方可**上传付款凭证**（转账回单等附件）或在线说明，收款方/工作人员**确认收款**计入台账（支持部分履行），收款方也可提出**收款异议**。每日扫描到期未付节点自动置逾期并预警（「立即扫描逾期」按钮用于演示）。
7. **逾期回访与履行观察（随反馈重新计算）**：某一期逾期后**调解员发起逾期回访**；回访后双方可上传**未付款说明**或**收款异议**，调解员根据双方反馈决定是否**继续履行观察**——继续的案件进入「履行观察期」，观察期内当事人再次反馈的，**观察期自反馈之日重新计算**；不再观察则维持逾期。观察期届满仍未足额履行的，案件**自动恢复逾期**并移交法官助理；观察期内全部付清则自动履行完毕。
8. **法官助理同步判断与后续执行线索**：法官助理同步查看逾期回访与双方反馈，判断**维持跟踪 / 进入司法确认 / 移送后续执行线索 / 建议转立案**；选择执行线索时可一并登记财产/收入/担保人/行踪等**执行线索**，执行联络据以移送或办结。
9. **常规回访**：执行联络/法官助理登记电话/线上/上门回访与结果。
10. **司法确认**：申请后案件进入审查中，可下载《司法确认申请书》，法官助理审查通过后转入履行跟踪。
11. **转立案**：选择失联/证据争议/拒绝调解/协议逾期等原因，系统**自动汇编**申请、分流意见、历次排期改期、笔录、协议签署、履行、付款凭证/未付款说明/收款异议、逾期回访与履行观察、执行线索、回访、送达、失联说明为材料包，窗口一次接收并登记诉讼案号，当事人无需重复补交。
12. **连续过程材料卷**：案件详情页「导出连续过程材料卷」随时把全过程时间线汇编成文本下载，供法官查阅。
13. **批量导入**：「批量导入」页支持 CSV 文件上传或粘贴，自带模板，逐行返回成功编号与失败原因。
14. **统计看板**：调解效率（成功率、在办、待分流）、案由分布、状态分布（含履行观察期）、协议履行到位率/已付总额/逾期节点、待跟进执行线索、转立案原因分布、多次改期/失联/缺件风险统计（ECharts 图表）。
15. **角色工作台**：登录后首页按角色生成待办（窗口待分流/材料待接收、调解员待排期待调解失联联系与逾期回访/履行观察、当事人凭证上传/收款异议/逾期告知、法官助理司法确认与转立案审核及逾期回访判断、执行联络分期与逾期回访、执行线索移送）。

### 已实际执行的验证

构建与回归均在本仓库当前代码上实际执行（JDK 17 / Maven 3.8 / Node 22）：

1. **前端构建**：`cd frontend && npm run build` 成功，产物输出到 `backend/src/main/resources/static`。
2. **后端编译打包**：`cd backend && mvn clean package -DskipTests` 成功，产出 `backend/target/mediation-platform.jar`（约 52MB，含前端静态资源）。
3. **分期履行跟踪闭环端到端回归**（`python3` 标准库脚本对运行中的 jar 实际调用，**42 项断言全部通过**），覆盖：
   - 六类角色登录与无令牌 401 拦截；附件下载无令牌 401、鉴权后可下载且字节一致；
   - 申请→分流→笔录→协议→人脸（1234 通过）→双方签署→建立 3 期计划；
   - **按期提醒**：临期/到期未结清节点被提醒、远期节点不提前提醒；

   - **调解员发起逾期回访**→双方提交**未付款说明 / 收款异议**（异议状态 DISPUTED、说明关联回访）；
   - **决定继续履行观察**→案件 OBSERVING、观察截止=今天+7、回访 OBSERVING；观察期内再反馈→**观察期重新计算并留痕**；

### 手工快速复验建议（分期履行跟踪闭环）

- 用 `zhang/mediator123` 登录，在一个调解中案件走「笔录 → 协议（选分期）→ 人脸（输 1234）→ 双方签署 → 建立 2~3 期计划（把首期到期日填到过去）」；
- 「履行与回访」页点「立即发送按期提醒」「立即扫描逾期」，看到按期提醒与逾期预警；
- 当事人/工作人员「上传付款凭证」（可附图片）→「确认收款」；再「发起逾期回访」→分别提交未付款说明、收款异议→「继续观察/重算」，观察案件进入「履行观察期」且横幅显示截止日；观察期内再提交一次说明，可见**观察期重新计算**；
- 用 `assistant/assistant123` 登录同一案件，对回访点「法官判断」，分别体验进入司法确认、移送执行线索（同步登记线索）；用 `execution/exec123` 移送线索；

## 说明与边界（演示环境）

- 人脸核验、电子送达、电子签名为**业务流程级模拟实现**（返回确定性模拟结果并完整留痕），接入真实能力时替换 `MediationService.faceVerify`、`DeliveryService.send` 即可，表结构已预留核验得分/证件后四位/送达签收字段。
- 付款凭证/收款异议等附件存于服务端本地目录（`app.upload.dir`，默认 `./data/attachments`；Docker 内为命名卷），仅做登录鉴权后的上传/下载演示，未做病毒扫描与对象存储；生产可替换 `AttachmentStorage`。
- 履行跟踪定时任务：按期提醒（启动后约 40s、其后每日一次，提前 `app.performance.remind-days`=3 天）、逾期扫描（约 30s/每日）、履行观察期届满扫描（约 50s/每日）；页面均提供“立即…”按钮便于演示，观察期天数由 `app.performance.observe-days`=7 控制。
- 令牌存于内存，服务重启需重新登录；H2 为内存库，重启后数据由种子程序重新初始化。
- 金额单位均为人民币元；时间为服务器本地时间。
